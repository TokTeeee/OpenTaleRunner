# 多人联机系统设计文档

艾瑟兰多人联机模式设计。

---

## 一、介绍

### 1.1 是什么

多人联机系统允许 2-10 名玩家在同一个游戏房间内协作冒险。每个玩家独立控制自己的角色，按回合制提交行动。一轮中所有玩家行动（或跳过）后，服务端汇总并调用多人 PM 引擎生成统一的叙事结果，广播给所有客户端。

### 1.2 核心概念

| 概念 | 说明 |
|---|---|
| **房间 (Room)** | 独立的游戏会话，由房主创建。每个房间有唯一的雪花 ID |
| **回合 (Round)** | 所有玩家提交行动 → GM 生成叙事 → 后果应用 → 进入下一回合 |
| **角色槽 (Slot)** | 继承存档时，预定义的角色槽需要由真实玩家认领后游戏才能开始 |
| **观战 (Spectating)** | 游戏中途加入的玩家先以观战者身份进入，满足条件后由 GM 引入 |
| **心跳 (Heartbeat)** | 客户端每 30 秒向服务端报告在线状态 |

### 1.3 关键设计决策

| 决策 | 说明 |
|---|---|
| 房主本地存档 | 多人存档由房主客户端本地存储（localStorage），不上传服务器 |
| 存档隔离 | 多人存档仅供多人模式使用，单人存档不能直接用于多人 |
| 继承存档 | 创建房间时可选择继承已有的多人存档，恢复上次游戏进度 |
| 强制组队 | V1 不允许玩家分离探索，所有玩家保持队伍状态 |
| 行动轮同步 | 每轮所有玩家必须行动结束（或跳过）后才进入下一轮 |
| 背包独立 | 每个玩家的角色属性、背包、状态完全独立 |
| 异步容错 | 支持玩家暂时离线，可重新连接恢复 |

## 二、设计

### 2.1 房间生命周期

#### 创建房间

```
房主: POST /api/v1/multiplayer/rooms { mode: "new"|"inherit", config: RoomConfig }
  |
  ├─ mode="new": 全新开始
  │    └─ 服务端创建空房间 (phase="waiting")
  │
  └─ mode="inherit": 继承存档
       └─ 上传存档中的角色数据 → 服务端创建房间 + 加载角色槽
            └─ 房主自动认领匹配的角色槽
```

**RoomConfig 字段**（`client/src/types/multiplayer.ts:27`）：**18 个字段, 旧文档仅列 10 个**——

| 类别 | 字段 | 类型/范围 | 默认 | 备注 |
|------|------|----------|------|------|
| 基本 | `roomName` | `string` (1-30字) | `'冒险小队'` | |
| 基本 | `maxPlayers` | `number` (1-10) | `4` | |
| 基本 | `password` | `string?` (≥4字符) | `undefined` | |
| 故事 | `storybookId` | `string?` | `undefined` | |
| 故事 | `startingRegion` | `string?` | `undefined` | |
| 故事 | `narrativeStyle` | `NarrativeStyle` | `'detailed'` | |
| 故事 | `narrativeLanguage` | `NarrativeLanguage` | `'zh'` | |
| 规则 | `difficultyModifier` | `number` (-5 ~ +5) | `0` | |
| 规则 | `allowNpcRecruitment` | `boolean` | `true` | |
| 规则 | `enableFastTravel` | `boolean` | `true` | |
| 规则 | `deathPenalty` | `DeathPenalty` | `'soft'` | |
| 规则 | `restRecoveryMultiplier` | `number` (0.5 ~ 2.0) | `1.0` | |
| 轮次 | `actionRoundTimeout` | `number` (60-600秒) | `300` | 客户端 UI 当前未提供该值的手动设置入口，房主只能用服务端默认 `300s` |
| 轮次 | `autoSkipOnTimeout` | `boolean` | `true` | |
| 轮次 | `allowSkipAction` | `boolean` | `true` | |
| 管理 | `allowLateJoin` | `boolean` | `true` | |
| 管理 | `lateJoinIntroDelay` | `number` (1-5轮) | `2` | 与"观战延迟"对应 |
| 管理 | `allowSpectators` | `boolean` | `false` | |

#### 加入房间

```
玩家: POST /api/v1/multiplayer/rooms/{id}/join { password?, claimed_slot_id? }
  |
  ├─ phase="waiting" → 进入等待大厅
  │    ├─ mode="inherit": 可认领指定角色槽或自动分配第一个未认领槽
  │    └─ mode="new": 开始角色创建
  │
  └─ phase="playing" + allow_late_join=true → 以观战者身份加入
       └─ phase="playing" + allow_late_join=false → 拒绝（游戏已开始）
```

#### 开始游戏

房主确认所有玩家就绪后点击"开始游戏"：
- 全新开始：GM 读取所有玩家出身背景，生成统一起始故事背景和共同起始地点
- 继承存档：直接加载存档中的世界状态和起始位置

#### 离开与销毁

- 玩家离开 → 释放认领的角色槽
- 最后一位玩家离开 → 房间自动删除
- 房主离开且剩余玩家 → 房主转移给第一位剩余玩家
- 所有玩家离线且房间空闲 > 30min → 自动删除
- 等待阶段房间超过 24h → 自动删除

### 2.2 回合系统

#### 行动提交流程

```
每个玩家:
  1. 输入行动文本 (1-2000 字符)
  2. 客户端本地掷骰 → 生成 diceResult
  3. POST /api/v1/multiplayer/rooms/{id}/action { action, dice_result? }
  4. 服务端记录行动和骰子结果，标记该玩家"已行动"

所有玩家行动完毕（或跳过）后:
  1. 客户端检测 pendingPlayers.length === 0
  2. 调用 POST /api/v1/multiplayer/rooms/{id}/round-process
  3. 服务端: conflict_detector → multiplayer_pm.generate_narrative() → 返回 RoundResult
  4. 各客户端: syncRoundResultMessages() → applyConsequences() → 进入下一轮
```

#### 跳过 (Skip)

```
POST /api/v1/multiplayer/rooms/{id}/action-skip
  → 等同于提交 action="跳过"
```

#### 回合状态轮询

| 轮询 | 间隔 | 内容 |
|---|---|---|
| Room Poll | 5s | 房间整体状态（phase, players, slots） |
| Round Poll | 3s | 当前轮次状态（players_acted, pending_players, actions, dice_results） |

客户端自动检测：当 `pendingPlayers.length === 0` 且本地 `lastProcessedRound < currentRound` 时，自动触发 `processRound`。

### 2.3 玩家管理

#### 玩家状态

| 状态 | 含义 |
|---|---|
| `waiting` | 在等待大厅，尚未完成角色创建 |
| `ready` | 角色就绪（继承模式：已认领角色槽） |
| `in_game` | 游戏中，参与行动轮 |
| `spectating` | 中途加入，观战中 |
| `pending_intro` | 观战者完成角色创建，等待 GM 引入 |
| `disconnected` | 心跳超时（90s 无心跳标记离线） |

#### 观战者引入

```
观战者加入 → status="spectating", joined_at_round = current_round
  │
  ├─ 完成角色创建 (spectator_ready) → status="pending_intro"
  │
  └─ 每轮 process_round 时检查:
       rounds_waited = current_round - joined_at_round + 1
       若 rounds_waited >= late_join_intro_delay → 引入
         status="in_game", 生成 introduced_players 通知
```

#### 房主转移

房主离开时，第一位剩余玩家自动成为新房主（通过删除+重建房间行实现）。

### 2.4 同步机制

#### 客户端轮询架构

```
startHeartbeat()     → 每 30s: POST /heartbeat
startRoomPoll()      → 每 5s:  GET /rooms/{id} → syncRoomSnapshot()
startRoundPoll()     → 每 3s:  GET /rooms/{id}/round-status → updateRoundStatus()
startRealtimeSync()  → 每 30s: PUT /sync/session (单人模式)
```

#### 重连机制 (ReconnectService)

- 监听 `online`/`offline` 浏览器事件
- 断线后指数退避重试：`delay = max(15000, 2000 * (attempts + 1))`
- 重连后：获取房间状态 → 获取轮次状态 → 拉取缺失的叙事历史 → 同步消息到 gameStore

#### 单人实时同步

独立于多人房间：每 30s 上传角色位置/区域/行动/状态，轮询附近在线玩家用于幽灵 NPC 展示。

### 2.5 GM 集成

#### 多人叙事生成 (multiplayer_pm.py)

```
process_round() 触发:
  1. conflict_detector.detect() → 检测玩家行动冲突（目标冲突）
  2. multiplayer_pm.generate_narrative():
     - 构建 Prompt: world_day + round + location + party_members + actions + conflicts
     - 调用 LLM (与服务端相同配置)
     - 提取 <consequences> JSON 块
  3. 生成 RoundResult:
     {
       narrative: "统一叙事文本",
       consequences: { playerId: { hpChange, itemsGained, stateChanges } },
       world_state_changes: [],
       introduced_players: [...],
       next_round: N+1
     }
```

#### 后果应用 (客户端)

```
syncRoundResultMessages() → 构建 Message 对象
  ├─ round_summary (玩家行动 + 骰子)
  ├─ pm (叙事文本)
  └─ system (引入玩家通知)

applyMultiplayerConsequenceIfNew() → 去重检查 → applyConsequences()
  └─ 直接修改本地角色状态 (HP/物品/状态)
```

### 2.6 服务端架构

```
routers/multiplayer_router.py  (HTTP 端点，18 个)
    │
    v
services/multiplayer_service.py  (业务逻辑，房间锁，回合编排)
    │                    │
    v                    v
repositories/           services/multiplayer_pm.py
multiplayer_repo.py     (LLM 叙事生成)
(SQLite 数据访问)
```

#### 房间级锁

所有关键操作（join/leave/submit/process）使用 `asyncio.Lock` 保证并发安全，加入操作使用双重检查锁定。

#### 后台任务

| 任务 | 周期 | 说明 |
|---|---|---|
| 心跳检查 | 30s | 标记离线 (>90s)、自动跳过超时动作、移除长时间离线玩家、清理空房间 |
| 等待清理 | 30s | 24h 无活动的等待中房间自动删除 |

#### 数据库

| 表 | 说明 |
|---|---|
| `multiplayer_rooms` | 房间配置、状态、行动、骰子、角色槽、叙事历史、通知 (JSON 列) |
| `room_player_sessions` | 每玩家会话数据 (状态、心跳、角色信息) |

### 2.7 客户端架构

```
hooks/pmEngine/useMultiplayerSync.ts
  └─ hydrateMultiplayerScene()  ← 进入多人模式时调用
  └─ syncRoundResultMessages()  ← 回合结果同步
  └─ applyMultiplayerConsequenceIfNew()  ← 后果应用

hooks/pmEngine/useActionSubmit.ts
  └─ submitAction()  ← 分支: 多人模式 vs 单人模式

services/multiplayer/MultiplayerAPI.ts
  └─ 18 个 API 函数 (createRoom/joinRoom/submitAction/...)

services/sync/HttpClient.ts
  └─ request<T>()  ← 统一的 HTTP 客户端 (base URL + auth 注入)
```

## 三、规划

### 3.1 当前限制

| 限制 | 说明 |
|---|---|
| 无 WebSocket | 所有同步基于 HTTP 轮询，延迟 3-5s |
| 无 PvP | 不支持玩家间直接冲突互动 |
| 纯内存锁 | 房间锁为单进程 asyncio.Lock，不支持多 worker 部署 |
| 存档仅房主 | 多人存档只能由房主客户端保存，其他玩家不能独立存档 |
| 冲突检测简化 | 仅检测 `target_conflict` 类型，未实现 `space_conflict`/`causal_conflict` |
| 无房间列表 | 没有公开房间浏览/搜索功能，只能通过 ID 加入 |
| 纯观战未实现 | `allowSpectators` 配置存在但未生效，观战者必须意图加入游戏 |

### 3.2 未来规划

期望引入 WebSocket 实时同步机制，将状态同步延迟从秒级轮询降至毫秒级推送，让每位玩家的操作都能即时反馈到同一房间的所有客户端。进一步采用分布式锁方案，为服务端多 Worker 水平扩展铺平道路，支撑更大规模的并发房间与更稳定的在线体验。

期待打造完整的 PvP 冲突系统，在现有 PvE 协作基础上引入玩家间的对抗互动，从简单目标冲突逐步扩展至空间冲突和因果冲突的全维度覆盖。同时上线公开房间浏览功能，让玩家可以搜索、筛选和发现正在等待冒险伙伴的房间，降低组队门槛。

希望实现纯观战模式，允许感兴趣的玩家以旁观者身份进入任何公开房间，无需承担游戏参与的负担。进一步解耦强制组队限制，允许队伍成员在安全区域内自由分离探索，享有更灵活的行动空间与叙事可能性。

计划将数据库从 SQLite 迁移至 PostgreSQL，充分利用其行级锁、并发写入和高级索引能力，支撑更高并发的多人在线体验与数据可靠性保障。
