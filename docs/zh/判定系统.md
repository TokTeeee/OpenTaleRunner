# 判定系统

## 一、介绍

判定系统（Judgment System）是 OpenTaleRunner 的核心决议机制，负责裁定角色在游戏世界中的所有行动结果。系统采用 2d6 骰子池，通过多来源修饰符叠加与难度等级（Difficulty LC）比对，将每次行动映射为五档分级结果。

**为何使用 2d6？** 2d6 产生 2~12 的钟形分布，峰值在 7，相比 d20 的均匀分布更贴近真实世界——大多数尝试趋近平均表现，极端成功与极端失败较少见。这为叙事驱动的判定提供了更自然的概率基础。

**核心概念：**

- **荒诞等级（absurdity）**：GM 对行动难度的主观评估，取值 1~10。值越大表示行动越离谱/越困难。
- **难度等级（difficultyLC）**：由 absurdity 通过映射表 `absurdityToLC` 转换为 2~16 的固定值，代表该行动需要通过的门槛。
- **结果分级（outcome tiers）**：判定最终分为 critical_success、success、partial_success、failure、critical_failure 五档，不同档次触发不同的叙事与数值后果。

当 absurdity ≤ 2 时，行动视为**自动成功**，无需掷骰。

## 二、设计

### 2.1 完整公式

判定计算分为两阶段：

**阶段一：原始最终值**
```
rawFinalResult = diceTotal(2d6) + attrMod + skillLevel + equipBonus + totalPartyBonus - condPenalty - nightPenalty
```

其中 `totalPartyBonus` 是 `partyBonus.totalDamageBonus + partyBonus.totalDefenseBonus + partyBonus.totalSkillBonus` 三种加成之和（取自 `PartyStore.getCombatBonus()`）。当设置 `experimental.enableSystemHooks` 时，hook 系统还可以通过 `combat.beforeRoll` 进一步注入 `hookBonus` / `hookPenalty`。

> `partyBonus` 是"三种加成之和"——`totalDamageBonus + totalDefenseBonus + totalSkillBonus`——没有"成员行为计数"等其他含义。

> `JudgmentSystem.evaluate()` 当前不读取场景修正参数——由后续系统按需扩展。

**阶段二：阈值判定**
将 rawFinalResult 与阈值表比对照出 outcome。随后计算存储值：
```
storedFinalResult = rawFinalResult - difficultyLC
```

storedFinalResult 用于后续系统（如伤害计算）的强度量化，正数表示超出预期的优异表现，负数表示力有不逮。

### 2.2 absurdity→LC 映射表

| absurdity | difficultyLC | 说明 |
|-----------|--------------|------|
| 1 ~ 2     | 2            | 极其简单；≤2 自动成功，无需掷骰 |
| 3 ~ 4     | 5            | 简单 |
| 5 ~ 6     | 8            | 普通 |
| 7 ~ 8     | 12           | 困难 |
| 9+        | 16           | 极难/荒诞 |

### 2.3 修饰符来源

各修饰符的计算逻辑：

- **属性修正（attributeModifier）**：`floor((attr - 10) / 2)`，其中 attr 来自角色对应属性值。
- **技能加成（skillBonus）**：`skill.level`，直接取角色的技能等级。
- **装备加成（equipmentBonus）**：`weapon + armor + accessory` 三类装备的效果值之和。具体提取逻辑见 2.6。
- **队伍加成（partyBonus）**：队伍中**有意识**（conscious）成员的战力（combat ability）之和。
- **异常惩罚（conditionsPenalty）**：取所有匹配到的状态异常的 dicePenalty 的 **最大值**（Math.max），最严重的异常决定惩罚。详见 2.7。
- **夜间惩罚（nightPenalty）**：根据地下层级与游戏时钟决定，详见 2.5。

### 2.4 结果映射

| rawFinalResult | outcome          | 含义 |
|----------------|------------------|------|
| ≥ 12           | critical_success | 大成功 |
| ≥ 8            | success          | 成功 |
| ≥ 5            | partial_success  | 部分成功 |
| ≥ 0            | failure          | 失败 |
| < 0            | critical_failure | 大失败 |

### 2.5 夜间惩罚表

夜间惩罚（nightPenalty）受**地形（terrain）**与**游戏钟（clock）**共同决定：

| 条件 | 惩罚值 | 备注 |
|------|--------|------|
| 地形 = underground | 3 | 地下无条件惩罚 |
| clock ≥ 20 或 clock < 5 | 2（基础值） | 深夜时段，若无光源额外 +2 |
| clock < 6 或 clock ≥ 19 | 1 | 黄昏/清晨时段 |
| 其他（白天） | 0 | 无惩罚 |

其中：基础值为 2 时，若角色无光源（light source），最终惩罚 = 基础值 + 2 = 4。

### 2.6 装备效果解析

装备系统产生的效果类型多达十余种，判定系统仅关注其中的子集：

| 效果类型 | 处理方式 |
|---------|----------|
| damage_bonus | 计入 directBonus（装备加成的直接部分） |
| defense_bonus | **计入 directBonus**（与 damage_bonus 同样作为直接修正） |
| attribute_mod | 仅 STR 和 DEX 类型的属性修正计入 |
| skill_bonus | 计入 skillBonus |
| light_source | 影响夜间惩罚值（见 2.5） |
| hp / restore / vital / special | **忽略**，不参与判定公式 |

> `defense_bonus` 参与判定——代码在 `applyEffect()` 中将其与 `damage_bonus` 等同计入 `directBonus`。

### 2.6.1 Hook 系统加成（可选）

当 `experimental.enableSystemHooks` 开启时，判定前会向 `systemHooks.apply('combat.beforeRoll', ...)` 发布事件，外部规则可在事件载荷中返回 `hookBonus`（正数加值）和 `hookPenalty`（负数惩罚），最终：

- `equipBonus += hookBonus`（加入 `directBonus`）
- `condPenalty += hookPenalty`

详见 [GameRuleEngine 中间件设计文档](GameRuleEngine中间件设计文档.md)。

### 2.7 条件惩罚聚合

系统共定义 15 种异常状态（conditions），每种都携带一个 `dicePenalty` 字段。聚合规则：

- 遍历角色当前所有活跃的条件
- 取 `Math.max(...dicePenalties)` —— 即**最严重的异常获胜**，不叠加
- 未能识别的异常状态默认 penalty = 1

典型条件包括：中毒、麻痹、眩晕、失明、恐惧、沉默等。

### 2.8 API 示例

**接口定义：**
- `JudgeParams`：`{ absurdityLevel, difficultyLC, reason, relevantSkill, relevantAttribute }`
- `DiceResult`：`{ diceValues, total, attributeModifier, skillBonus, equipmentBonus, finalResult, outcome, conditionsPenalty, nightPenalty, partyBonus }`

**调用方式：**
```ts
const result = JudgmentSystem.evaluate(params, character, sceneContext);
```

**骰值格式化示例：**
```
"2d6: [4,5] +2(属性) +3(技能) +1(装备) -2(异常) = 13 vs DC8 → 成功"
```

### 2.9 相关系统

判定系统自身不孤立运行，与以下系统存在数据依赖与流程耦合：

| 系统 | 文件 | 交互方式 |
|------|------|----------|
| PM引擎 | `PM引擎与Prompt系统.md` | `evaluateAction()` 调用 LLM 获取 absurdity 值 |
| 物品系统 | `物品系统.md` | 装备效果解析后提供 equipmentBonus |
| 队伍系统 | `队伍系统.md` | 队员战力求和高提供 partyBonus |
| 安全系统 | `安全系统.md` | `crypto.getRandomValues` 提供安全随机掷骰 |
| 角色系统 | `角色系统.md` | 属性/技能/条件提供 attrMod、skillBonus、condPenalty |

## 三、规划

期望将元素伤害与抗性效果接入最终判定公式，让火焰、冰霜、雷电等属性不再只是标签，而是真正影响每一次掷骰的战术变量。同步将 `sceneModifier` 从硬编码解放，由 gameStore 实时读取环境修正，让场景氛围切实作用于角色命运。

在此基础上，探索多人冲突判定扩展——当多位玩家在时间与空间上交汇，系统应当能够感知并裁定 `space_conflict` 和 `causal_conflict` 等复杂互动场景，为多人联机的戏剧性碰撞提供公正而高效的决议机制。
