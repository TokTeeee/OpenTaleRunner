# 编年史系统

## 一、介绍

编年史系统是 OpenTaleRunner 的世界叙事记录与聚合机制，负责将每位冒险者的每一次行动（含判定结果）记录为结构化日志，在满足聚合阈值时由服务端大 PM（Grand PM）调用 LLM 生成区域级世界编年史叙事。

系统遵循"客户端记录 → 世界日结束时批量上传 → 服务端聚合"的异步流水线。离线期间未上传的日志自动缓存至 `localStorage`，下次联网时自动冲刷，确保网络中断不丢记录。

**核心概念：**

- **ChronicleRecorder**：客户端内存中的编年史日志缓冲区，记录玩家所有行动的判定结果与叙事输出。
- **世界日（worldDay）**：全服共享的逻辑日期计数器，由客户端 `startNewDay()` 推进，服务端按 `worldDay` 聚合日志。
- **Grand PM（大PM）**：服务端唯一的 LLM 调用点（`chronicle_engine.py`），以史官口吻将当日区域内的玩家日志汇总为世界编年史条目。
- **离线缓冲**：上传失败时，日志自动写入 `localStorage` 键 `aeslan-offline-logs`，下次成功上传后一并冲刷。

本系统与 PM 引擎（客户端叙事）、多人联机系统（玩家交互记录）、架构配置（环境变量阈值）紧密耦合 —— 详见末尾交叉引用。

## 二、设计

### 2.1 ChronicleRecorder（记录器）

**源码**：`client/src/services/chronicle/ChronicleRecorder.ts`

`ChronicleRecorder` 是客户端唯一的编年史日志内存缓冲区。全局单例由 `client/src/hooks/pmEngine/shared.ts:18` 初始化：

```ts
export const _chronicleRecorder = new ChronicleRecorder('player_local', '冒险者');
```

构造函数接收 `playerId`（默认 `'player_local'`）和 `characterName`（默认 `'冒险者'`），均可在角色加载后通过 `rebind()` 重新绑定。

**公开方法**：

| 方法 | 签名 | 说明 |
|---|---|---|
| `constructor` | `(playerId: string, characterName: string)` | 初始化空条目数组，绑定玩家身份 |
| `rebind` | `(playerId, characterName, clearEntries?)` | 切换角色时更新身份，可选择性清空缓冲区 |
| `recordEntry` | `(entry: Omit<ChronicleLogEntry, 'entryId'\|'playerId'\|'characterName'\|'syncStatus'>)` | 接收去除系统字段的日志，自动补全 `entryId`/`playerId`/`characterName`/`syncStatus` |
| `getEntries` | `(worldDay?: number) → ChronicleLogEntry[]` | 按世界日过滤返回（无参数返回全部副本） |
| `getPendingEntries` | `() → ChronicleLogEntry[]` | 返回所有 `syncStatus === 'pending'` 的条目 |
| `getRecentEntries` | `(limit: number) → HistoryEntry[]` | 返回最近 N 条的精简摘要（供历史回顾 UI 使用） |
| `packDailyLogs` | `(worldDay: number) → ChronicleLogBatch` | 打包指定世界日的所有 pending 条目为上传批次 |
| `markSynced` | `(entryIds: string[]) → void` | 将指定 ID 的条目标记为 `'synced'` |
| `toJSON` / `fromJSON` | `→ / ← ChronicleLogEntry[]` | 序列化/反序列化整个缓冲区（用于存档持久化） |
| `countByDay` | `(worldDay: number) → number` | 统计指定世界日的日志条数 |

**状态管理**：各条目持有独立 `syncStatus`，取值 `'pending' | 'synced' | 'failed'`。`recordEntry` 新增的条目默认 `'pending'`；`packDailyLogs` 仅打包 `pending` 且匹配世界日的条目；`markSynced` 由调用方在上传成功后批量扭转状态。

### 2.2 ChronicleLogEntry（日志条目）

**客户端类型**：`client/src/types/chronicle.ts`  
**服务端模型**：`server/models/chronicle.py → ChronicleLogEntry`

每次玩家提交行动并收到 PM 叙事后，`useActionSubmit` 构造一条 `ChronicleLogEntry`，字段如下：

| 字段 | 类型 | 来源/说明 |
|---|---|---|
| `entryId` | `string` | 客户端 `generateId()` 生成，服务端写入 `INSERT OR IGNORE` 防重 |
| `playerId` | `string` | ChronicleRecorder 绑定，单人模式为 `'player_local'` |
| `characterName` | `string` | 当前角色名 |
| `worldDay` | `number` | 服务器世界日计数 |
| `localDay` | `number` | 角色本地日（用于生命计量，与 `worldDay` 允许不对齐） |
| `location.region` | `string` | 当前区域（如 `王都平原`） |
| `location.subRegion` | `string` | 子区域（如 `南部村庄`） |
| `location.coordinates` | `{x, y, z}` | 角色当前坐标 |
| `action.summary` | `string` | 行动文本截取前 80 字 |
| `action.playerChoice` | `string` | 玩家原始输入全文 |
| `action.wasCustomInput` | `boolean` | 是否为自定义输入（当前始终 `true`） |
| `action.absurdityLevel` | `number` | 荒诞等级（1~10），由 `estimateAbsurdity()` 计算 |
| `action.difficulty` | `number` | 难度等级 LC，由 `absurdityToLC()` 映射 |
| `action.rollResult` | `string` | 判定结果（`critical_success` / `success` / `partial_success` / `failure` / `critical_failure`） |
| `action.rollDetail.dice` | `number[]` | 骰子值列表（通常 2 个 d6） |
| `action.rollDetail.modifier` | `number` | 属性/技能/环境修饰符总合 |
| `action.rollDetail.total` | `number` | 最终骰值（dice sum + modifier） |
| `action.rollDetail.dc` | `number` | 难度等级（同 `difficulty`） |
| `narrativeOutput` | `string` | PM 返回的完整叙事文本 |
| `consequences` | `Record<string, unknown>` | 后果对象（hpChange / stateChanges / skillsLearned 等） |
| `timestamp` | `string` | ISO 8601 时间戳 |
| `syncStatus` | `'pending' \| 'synced' \| 'failed'` | 同步状态，仅客户端侧维护 |

**服务端差异**：服务端 `ChronicleLogEntry`（Pydantic 模型）不包含 `syncStatus` 字段；该字段是客户端内部状态标记，不入库。服务端通过 `INSERT OR IGNORE` 以 `entryId` 为唯一键确保幂等。

### 2.3 服务端聚合（chronicle_engine.py）

**源码**：`server/services/chronicle_engine.py`

`ChronicleEngine` 是服务端唯一的 LLM 调用点，承担"大PM"角色。它在收到客户端日志后**触发式**执行聚合，无需定时轮询：

**调用链**：
```
POST /api/v1/chronicle/upload
  → chronicle_router.upload_chronicle()        # 入库 + 更新玩家活跃度
    → engine.aggregate_region(region, worldDay) # 每个条目按区域触发
```

**聚合流程**（`aggregate_region(region, worldDay)`）：

1. **阈值检查**：`chronicle_repo.get_recent_by_region(region, worldDay)` 查询该区域当日日志数。若 `< CHRONICLE_AGGREGATE_MIN_LOGS`（环境变量，默认 `1`），直接返回 `None` 跳过聚合。
2. **组装摘要**：每条日志提取 `characterName`、`action.summary`、`action.rollResult`，拼为 `- 名字: 摘要 → 判定结果`。
3. **构造 Prompt**：`_build_prompt()` 生成约 300 tokens 的史官指令，要求 200-400 字第三人称史诗叙事，第一行为 `#` 标题。
4. **LLM 调用**：POST 到 `llm_endpoint`，模型/温度/最大 token 由环境变量控制。失败或未配置 API Key 时回退到 `_fallback_aggregate()`，只输出区域事件计数。
5. **结果解析**：首行去除 `#` 前缀作为标题，余文作为叙事体。
6. **入库**：`INSERT OR REPLACE INTO world_chronicle`，以 `wc_{worldDay}_{region}` 为主键，确保同一区域同日只保留最新聚合结果。

**关键配置**（`server/config.py`）：

| 环境变量 | 默认值 | 说明 |
|---|---|---|
| `SERVICE_LLM_KEY` | — | LLM API Key（为空时启用 fallback） |
| `SERVICE_LLM_ENDPOINT` | `https://api.deepseek.com/chat/completions` | LLM 端点 |
| `SERVICE_LLM_MODEL` | `deepseek-chat` | 模型名 |
| `SERVICE_LLM_TEMPERATURE` | `0.7` | LLM 温度 |
| `SERVICE_LLM_MAX_TOKENS` | `2048` | 最大输出 Token |
| `CHRONICLE_AGGREGATE_MIN_LOGS` | `1` | 触发聚合的最小日志数 |

**数据表**：

- `chronicle_entries` — 原始日志，以 `entryId` 为主键，`INSERT OR IGNORE` 防重
- `world_chronicle` — 聚合后的编年史叙事，以 `wc_{worldDay}_{region}` 为主键

### 2.4 世界日推进（startNewDay）

**源码**：`client/src/hooks/pmEngine/useDayTransition.ts`

`startNewDay()` 是玩家的"休息/过夜"操作，完整流程如下：

```
startNewDay()
  ├─ game.setDay(currentDay + 1)          # 世界日 +1
  ├─ game.setDiceResult(null)             # 清空上次骰子结果
  ├─ game.addDayDivider(newDay)            # 消息流插入日分隔线
  ├─ character.updateVital(...)            # 恢复疲劳/饥饿/卫生/士气
  ├─ character.updateHP(...)              # 恢复 5 HP（上限 maxHp）
  ├─ game.addMessage(system, '一夜休整...')  # 系统提示
  │
  ├─ packDailyLogs(game.currentDay)       # 打包当日所有 pending 日志
  ├─ [如有日志] uploadChronicle (3 次重试)   # → 详见 2.5
  └─ requestScene()                       # 拉取新一天的场景
```

**恢复数值**：`{ fatigue: -30, hunger: +10, hygiene: +5, morale: +5 }`，HP 恢复 5 点（不超过 `maxHp`）。

**时间线不对齐**：每个角色的 `localDay`（用于生命计量）与 `worldDay`（用于编年史聚合）允许分离。服务端按 `worldDay` 聚合，不同玩家可能处于不同 `worldDay`——加速型玩家先到达高世界日，放缓型玩家留待后补。

### 2.5 上传重试机制

上传发生在 `startNewDay()` 中，采用 **3 次尝试 + 线性退避**（`useDayTransition.ts:38-65`）：

| 尝试 | 退避延迟 | 累计等待 |
|------|----------|----------|
| 第 1 次失败 | 2 秒后 → 尝试 2 | 2s |
| 第 2 次失败 | 4 秒后 → 尝试 3 | 6s |
| 第 3 次失败 | 写入离线缓冲 (不再重试) | — |

**真实代码路径** (`useDayTransition.ts:38-65`):
```typescript
for (let retry = 0; retry < 3 && !uploaded; retry++) {
  try {
    await api.uploadChronicle(batch);
    uploaded = true;
    // ... 成功路径: 冲刷离线缓冲 ...
  } catch (e) {
    if (retry === 2) {
      // 第 3 次失败 (retry===2) → 写入 localStorage 'aeslan-offline-logs'
    } else {
      await new Promise(r => setTimeout(r, 2000 * (retry + 1)));
    }
  }
}
```

**成功路径**（任意一次尝试成功时）：
```
uploadChronicle(batch) ✅
  → 尝试冲刷 localStorage 离线缓冲
    → 有缓冲：打包为 offlineBatch，追加 uploadChronicle → 删除 localStorage 键
    → 无缓冲/冲刷失败：静默继续
```

**失败路径**（3 次全部失败）：
```
uploadChronicle(batch) ❌
  → 第 3 次仍失败
    → 读取 localStorage 'aeslan-offline-logs'
    → 合并本次失败条目 [existing, ...batch.entries]
    → 写回 localStorage
```

退避延迟使用 `setTimeout(r, 2000 * (retry + 1))`：第 1 次失败 2s 后重试，第 2 次失败 4s 后重试（累计 6s），第 3 次失败直接写离线缓冲。

> **已知约束**：当前重试是 **"3 次尝试 + 线性退避"** 而非传统意义上的"指数退避"——延迟序列为 `2s / 4s`，第 3 次不再延迟而直接写离线缓冲。这是 `useDayTransition.ts:38-65` 的硬编码行为。如需实现真正的指数退避（如 `2s/4s/8s` 或 `1s/2s/4s/8s`），需同步修改客户端重试逻辑与服务端超时容忍阈值，并补全"重试参数配置项"——目前未列入计划。

### 2.6 离线缓冲（localStorage）

**键名**：`aeslan-offline-logs`  
**格式**：`ChronicleLogEntry[]` 的 JSON 序列化数组  
**写入时机**：上传失败 3 次后  
**读取时机**：下次成功上传后立即冲刷  
**删除时机**：冲刷成功后 `localStorage.removeItem('aeslan-offline-logs')`

冲刷时构造的离线批次复用同一 `playerId` 和 `lastWorldDay`：

```ts
const offlineBatch = {
  playerId: batch.playerId,
  entries,
  lastWorldDay: game.currentDay
};
await api.uploadChronicle(offlineBatch);
localStorage.removeItem('aeslan-offline-logs');
```

冲刷失败（网络问题或服务端异常）不会阻塞主流程，静默忽略，离线条目留待下一次上传再冲刷。

## 三、规划

期望实现增量同步机制，将当前"世界日结束时批量上传"改为每次记录即时推送，缩小数据丢失风险窗口，让编年史的每一笔都实时落地。同步引入冲突合并能力，当离线缓冲冲刷与正常上传产生竞态时，服务端能够智能去重，确保世界历史不被重复记录污染。退避策略与重试参数也将从硬编码提升为可配置项，适应不同网络环境。

在此基础上，探索跨世界编年史体系——每个游戏世界拥有独立的编年史卷册，新玩家加入新世界时不必背负旧世界的全部历史记忆。同时支持跨世界叙事引用，让第二世界的某座遗迹能优雅地提及第一世界英雄的传说，为世界间伏笔编织提供数据骨架。每隔若干世界日生成编年史快照，作为世界状态的检查点，支撑"时光回溯"的叙事需求。

远期期望将编年史推向社区——从请求驱动的聚合升级为事件队列驱动的异步引擎，日志入库即入队，大 PM 的工作流更加稳健。社区看板将支持时间线滚动、区域热力图和玩家贡献排行等可视化维度。开放只读 Public API，允许社区工具与网站消费世界编年史数据构建第三方时间线。最终支持世界线分叉，同一区域同日可容纳多版编年史叙事，由分支 ID 区分，让世界的命运真正掌握在玩家手中。
