# 安全系统

> 艾瑟兰的安全设计覆盖客户端密钥保护、Prompt 注入防护、XSS 输出过滤、服务端认证鉴权与速率限制。

---

## 一、介绍

安全系统分为客户端和服务端两层。客户端负责保护用户自设的 AI API Key 不被明文暴露在浏览器存储中，并对发往 LLM 的用户输入做注入防护、对 LLM 返回的文本做 XSS 过滤。服务端通过 JWT 认证、Token 黑名单、速率限制和 CORS 白名单保障 API 安全。

---

## 二、设计

### 2.1 API Key 加密存储

**威胁模型**: 浏览器 DevTools、恶意扩展、物理磁盘访问可读取 `localStorage` 中的明文 Key。

**实现**: `services/crypto/CryptoService.ts`

| 环节 | 算法/机制 |
|---|---|
| 加密 | AES-256-GCM（Web Crypto API） |
| 密钥派生 | PBKDF2，100,000 次迭代，SHA-256 |
| 派生材料 | 设备唯一种子（`aeslan-device-seed`）+ 应用盐（`aeslan-crypto-v1`） |
| 设备种子 | 32 字节随机值，首次使用时生成，存储于 `localStorage` |
| 密文格式 | `$AESLAN1$<base64(12字节随机IV + 密文)>` |
| IV | 每次加密生成新的 12 字节随机 IV |

**加密字段**（Zustand persist 管线自动处理）：

```
llm.apiKey
autoPlayLLM.apiKey
stt.apiKey
tts.apiKey
imageGen.apiKey
token (auth)
```

**持久化流程**: `createSecureStorage()` 返回 Zustand persist 兼容的存储适配器。`setItem()` 时加密所有敏感字段后写入 `localStorage`，`getItem()` 时解密。非敏感字段直通。

**局限性**: 仅浏览器端保护；无硬件安全模块；无法防御同进程内存读取。

### 2.2 Prompt 注入防护

`sanitizePromptInput(text: string): string` 在每次 LLM 调用前对用户输入执行 **18 种正则替换**：

| 攻击向量 | 防护 |
|---|---|
| Markdown 标题注入 (`###`) | → `# # #` |
| 分隔线注入 (`---`) | → `- - -` |
| 代码块闭合 (` ```json ``` `) | → ` ` ` ` json ` ` ` ` ` |
| 代码块 (` ``` `) | → ` ` ` ` |
| JSON 注入 (`{"action_type":`) | → `{ " action_type "` |
| System 标签 (`<system>`, `</system>`) | → `&lt;system&gt;` |
| Instruction 标签 (`<instruction>`, `</instruction>`) | → `&lt;instruction&gt;` |
| **User 角色伪装** (`<user>`, `</user>`) | → `&lt;user&gt;` |
| **Assistant 角色伪装** (`<assistant>`, `</assistant>`) | → `&lt;assistant&gt;` |
| **Human 角色伪装** (`<human>`, `</human>`) | → `&lt;human&gt;` |
| **AI 角色伪装** (`<ai>`, `</ai>`) | → `&lt;ai&gt;` |
| 指令覆盖 (`ignore previous instructions`) | → `[instruction redacted]` |
| 全局覆盖 (`ignore all previous`) | → `[instruction redacted]` |

> `sanitizePromptInput` 实际覆盖 6 对开闭标签（system / instruction / user / assistant / human / ai，共 12 条角色标签模式），全部走相同转义路径。历史曾仅防护 4 条 system/instruction 模式，存在 `<user>hi</user>` 角色伪造绕过风险。

调用位置：`useActionSubmit` 中 `sanitizePromptInput(action)` 作为 `playerAction` 传入 PM 引擎。

### 2.3 敏感信息过滤

`redactSecrets(input: string): string` 在日志记录前对 LLM Prompt 响应做脱敏：

| 匹配模式 | 替换 |
|---|---|
| `apiKey` / `password` / `token` / `secret` 等字段值 | 整段替换为 `[REDACTED:fieldName]` |
| `sk-*` (OpenAI) / `gsk-*` (Groq) / `AIza*` (Google) | 整段替换为 `[REDACTED:apikey]` |
| `Bearer <token>` | → `Bearer [REDACTED]` |
| JWT (`xxx.yyy.zzz` 形式) | → `[REDACTED:jwt]` |
| `aeslan-` 前缀 (项目内部 API Key) | → `aeslan-[REDACTED]` |

> `redactSecrets` 通过 `ClientLogger.createEntry()` 集成——对 `message` 字段直接调用，对 `data` 字段用 `redactObject<T>()` 递归遍历。日志落入 `LogIndexedDB` 前已完成脱敏，无法事后回溯原始 LLM 响应中的 Key。

### 2.3 XSS 输出过滤

`sanitizeHtml(dirty: string): string` 使用 DOMPurify 过滤 LLM 返回的 HTML：

| 类别 | 策略 |
|---|---|
| 白名单标签 | `b`, `i`, `em`, `strong`, `br`, `p`, `ul`, `ol`, `li`, `span` |
| 白名单属性 | `class` |
| 其他一切 | 剥离 |

React 的自动转义（JSX 中 `{}` 插入的文本默认转义）是主防线，DOMPurify 作为 `dangerouslySetInnerHTML` 场景的第二防线。

### 2.4 服务端 JWT 认证

| 参数 | 值 |
|---|---|
| 算法 | HS256 |
| Payload | `{ sub: player_id, iat, exp, jti }` |
| 默认有效期 | 72 小时（`SERVICE_JWT_EXPIRE_HOURS`） |
| 密钥 | `SERVICE_JWT_SECRET`（必填，生产环境 `openssl rand -hex 32`） |

**Token 刷新**：`POST /api/v1/auth/refresh` — 使用当前有效 Token 换取新 Token。旧 Token 加入黑名单。

**Token 登出**：`POST /api/v1/auth/logout` — 将 Token SHA-256 哈希后加入内存黑名单。

**黑名单**: 内存 `dict[hash, expiry]`，`threading.Lock` 保护。`_blacklist_cleanup_loop(interval=600)`（`server/main.py:94`）由 `main.py:133` 的 `asyncio.create_task` 启动清理循环，不持久化（服务重启后清空）。

**新鲜度检查**: `require_fresh_token()` 依赖注入要求 Token 的 `iat` 在 300s 内（敏感操作如删除角色/解散房间）。

### 2.5 速率限制

| 参数 | 默认 | 环境变量 |
|---|---|---|
| 限制值 | 60 请求/窗口 | `SERVICE_RATE_LIMIT` |
| 窗口 | 60 秒 | `SERVICE_RATE_WINDOW` |
| 粒度 | 每 IP | — |
| 超限响应 | HTTP 429 | — |

实现为 FastAPI 中间件 `RateLimiter`（`server/middleware.py`），采用**固定窗口计数器算法**——`_buckets: dict[ip, (last_time, count)]`，窗口过期后重置计数；`threading.Lock` 保护多线程并发读写。

> **部署注意**：上述 `_buckets` 是**进程内字典**，ASGI 多 worker（如 gunicorn `-w 4`）部署时各 worker 独立计数，实际限流值 = `SERVICE_RATE_LIMIT × worker 数`。需要引入 Redis 等外部共享存储才能在多 worker 间统一限流。

### 2.6 CORS

可配白名单 `SERVICE_CORS_ORIGINS`（逗号分隔），默认 `http://localhost:5173,http://localhost:3000`。Dashboard（8081 端口）使用 `allow_origins=["*"]`（公开只读）。

## 三、规划

期望支持用户自定义主密码作为加密根密钥，替代当前依赖设备种子的派生方案，让用户对自身数据拥有完全的控制权。同步引入审计日志体系，完整记录登录、登出、Token 刷新与速率超限等安全事件，为安全审计和异常检测提供坚实的数据基础。

进一步探索 WebAuthn / Passkeys 等硬件安全模块认证能力，将登录安全提升到无需记忆密码的新等级。完善敏感操作保护流程，在删除角色、解散房间等关键操作前强制执行新鲜 Token 校验与用户二次确认，杜绝 CSRF 与回放攻击风险。

长期愿景是为角色数据与编年史条目提供可选的端到端加密能力，确保即使服务端也无法读取玩家的核心游戏数据，实现真正的数据主权与零信任架构。
