# 客户端架构与机制

> 本文以 `client/src` 当前实现为准，合并了架构设计、系统索引、运行流程与组件目录四部分内容。

---

## 一、分层架构

### 1.1 技术栈

| 层 | 当前实现 | 说明 |
|----|----------|------|
| 应用框架 | React 19 + TypeScript 6 + Vite 8 | 标准前端 Web Client 结构 |
| 状态管理 | Zustand 5 | `gameStore` / `characterStore` / `worldStore` 等按领域拆分 |
| 样式 | Tailwind CSS 4 + 全局样式表 | 原子类为主，辅以 `index.css` |
| 动画 | Framer Motion 12 | 叙事覆盖层和动效组件 |
| 网络层 | `fetch` + `EventSource` | REST 访问 + 世界更新 SSE 推送 |
| 本地持久化 | `localStorage` + `IndexedDB` | 设置、角色列表、联机存档、图片缓存 |
| AI 能力 | 客户端直连 LLM / TTS / Image API | 玩家自配密钥；服务端负责世界数据与多人房间状态 |

### 1.2 分层结构

```text
App / Components
  ├─ 负责标题页、单人界面、多人大厅/房间界面与模态装配
  ├─ 从各 store 读取状态并派发用户交互
  └─ 不直接实现复杂规则

Hooks Orchestration
  ├─ usePMEngine: 单人主循环 + 多人结果消费 + 后果落地
  ├─ useAutoPlay: 自动游玩控制编排
  ├─ useVoiceInput: STT 交互编排
  └─ useLocalization: 本地化访问

Domain Stores
  ├─ gameStore: 当前会话运行时状态
  ├─ characterStore: 当前角色状态
  ├─ worldStore: 服务端同步世界态
  ├─ multiplayerStore: 联机房间态
  ├─ npcStore / partyStore / autoPlayStore / uiStore / settingsStore
  └─ characterListStore: 本地角色索引

Services
  ├─ engine/: Prompt、Query、TokenBudget、History 压缩、PMEngine
  ├─ judgment/: 本地判定与条件效果
  ├─ sync/: 通用 APIClient 与世界同步管理
  ├─ multiplayer/: 多人 REST、轮询、心跳、存档
  ├─ hooks/: Game Hook System 与规则注册
  ├─ storybook/: 故事书运行时与字段规范化
  ├─ npc / party / travel / activity / autoPlay
  └─ tts / image / character card 等扩展能力

Server Interfaces
  ├─ 单人世界数据：storybook / world / sync / chronicle / activity
  ├─ 多人房间数据：multiplayer rooms / round / save / narratives
  └─ 媒体能力：LLM / TTS / Image 多为第三方 API
```

### 1.3 职责划分

**UI 层** — 以 `App.tsx` 为根装配点，根据 `phase`、多人房间状态和活跃模态决定渲染分支。布局组件负责状态映射为视觉结构，面板与模态组件负责局部交互，不承担跨系统业务编排。

**Store 层** — 保存"事实状态"，不发起复杂副作用：

- `gameStore`：当前时间、位置、消息、等待态、旅行态和骰子结果。
- `characterStore`：当前角色卡，提供属性、条件、物品、经历的原子更新。
- `worldStore`：Storybook、世界日、区域状态、世界编年史、幽灵 NPC 和待处理奇遇。
- `multiplayerStore`：房间快照、角色槽、大厅阶段、行动轮结果和联机存档索引。
- `settingsStore`：跨会话配置；`characterListStore`：本地角色目录。
- `npcStore`：已认识 NPC 注册表、关系、交互历史。
- `partyStore`：队伍成员、忠诚度、经验、战斗加成。
- `autoPlayStore` / `uiStore`：自动游玩进度与纯展示状态。

**Hook 编排层** — 承接组件行为，把多个 service 与 store 串起来：

- `usePMEngine`：单人主循环与多人结果消费的核心编排层，同时承担本地判定、后果落地、编年史记录和消息同步。
- `useAutoPlay`：把 `AutoPlayEngine` 与提交行动的主管线连接。
- `useVoiceInput`：浏览器语音识别或自定义 STT 结果塞回输入框。
- `useLocalization`：统一暴露本地化文案读取能力。

**Service 层** — 承载规则、IO 和跨 store 的公共能力：

- `PMEngine`：只负责 Prompt 与 LLM 往返，不直接写 store。
- `JudgmentSystem`：执行本地 2d6 判定，叠加属性、技能、装备、条件、夜间惩罚和队伍加成。
- `SyncManager`：世界态同步；`SyncServices`：房间轮询、心跳和实时附近玩家同步。
- `MultiplayerAPI` 和 `APIClient`：网络访问层，前者专注联机房间域，后者专注通用世界域。
- `SystemHooks`：规则订阅式联动，解耦时间流逝、休息、战斗、环境和条件效果。

### 1.4 关键数据通道

| 通道 | 入口 | 流程摘要 |
|------|------|----------|
| 单人主循环 | `InteractionArea` → `usePMEngine.submitAction()` | 本地判定 → LLM 叙事 → 后果落地 → 消息/编年史/存档 |
| 多人房间循环 | `MultiplayerAPI` + `SyncServices` | REST 请求 + 大厅/行动轮轮询 + 心跳 + `usePMEngine` 消费结果 |
| 世界同步 | `SyncManager`（playing 阶段启动） | 定时 `syncAll()` 上传编年史、拉取更新；SSE 推送写回 `worldStore` |
| 活动上报 | `ActivityReporter`（playing 阶段启动） | 周期上报位置、行动与在线状态 |

### 1.5 架构评估与演进方向

**合理之处：**

1. `store → hook → service` 分层已形成，单人、多人、世界同步和媒体能力都挂在明确边界上。
2. `SyncManager` 与 `SyncServices` 职责清晰——前者同步世界，后者同步房间与实时玩家，应保留此划分。
3. Storybook 运行时已成为世界设定的统一来源，不再依赖早期硬编码。

**待优化点：**

1. `usePMEngine.ts` 仍是偏重的 orchestration 层，同时承担单人推进、多人结果消费、后果落地、编年史记录和消息同步，测试与维护成本偏高。
2. `APIClient.ts` 与 `MultiplayerAPI.ts` 各自维护请求封装、鉴权和 JSON 适配，网络层存在重复实现。
3. 认证 token 归属不清晰，部分模块将其作为 `settingsStore` 字段读取，"认证会话"未独立为正式状态层。
4. 主 chunk 已超 500 kB，`SyncServices.ts` 中的动态导入因对应模块被静态引用而未形成实际分包收益。
5. `CacheManager.ts` 仍是预留型系统，需决定正式集成或清理。

**演进建议：**

1. 将 `usePMEngine` 拆为"动作提交""后果应用""多人结果消费""消息写回"四个更小的服务或 hook。
2. 抽取统一网络基础层，让 `APIClient` 与 `MultiplayerAPI` 共享 base request、鉴权和错误归一化逻辑。
3. 独立建设认证会话状态。
4. 针对多人、语音、图片和角色卡等次级能力做按路由或按交互分包，降低主 bundle 压力。

## 二、系统索引

### 2.1 根入口与总编排

| 系统 | 入口文件 | 主要职责 | 关键依赖 | 说明 |
|------|----------|----------|----------|------|
| 应用根入口 | `client/src/App.tsx` | 标题页、单人游玩、多人大厅/房间视图切换；装配 Storybook 运行时、全局模态、世界同步与活动上报生命周期 | `usePMEngine`、`useAutoPlay`、`SyncManager`、各 store | 系统装配层，不承载核心规则计算 |
| React 启动入口 | `client/src/main.tsx` | 挂载 React 根节点，导入全局样式并启动应用 | `App.tsx`、`index.css` | 不参与业务 |

### 2.2 状态管理系统（Stores）

| 系统 | 入口文件 | 主要功能 | 关键数据 | 备注 |
|------|----------|----------|----------|------|
| 游戏运行时状态 | `client/src/stores/gameStore.ts` | 管理当前阶段、时间、位置、消息流、选项、等待态、骰子结果、旅行状态 | `phase`、`currentDay`、`messages`、`coordinates`、`travelState` | 所有 UI 组件共享的短生命周期状态中心 |
| 当前角色状态 | `client/src/stores/characterStore.ts` | 管理当前玩家角色的属性、技能、HP、生活状态、物品、经历，并在条件变化时触发系统钩子 | `character`、`vital`、`inventory`、`recentHistory` | 只描述"当前角色"，不负责角色列表 |
| 世界同步状态 | `client/src/stores/worldStore.ts` | 保存 Storybook、世界日、区域状态、世界编年史、幽灵 NPC、奇遇与最近同步时间 | `storybook`、`regions`、`worldChronicle`、`ghostNPCs` | 服务端世界数据写回客户端的统一落点 |
| 界面状态 | `client/src/stores/uiStore.ts` | 管理模态框开关、侧栏折叠、字体与主题等纯展示状态 | `activeModal`、面板折叠状态 | 不应承载领域业务数据 |
| 设置状态 | `client/src/stores/settingsStore.ts` | 持久化 LLM、服务器、语音、图片生成、实验开关等运行配置 | `llm`、`server`、`tts`、`imageGen`、`experimental` | 通过 `persist` 跨会话保存 |
| 认证会话 | `client/src/stores/authStore.ts` | 独立于 settingsStore 的 token 持久化（`aeslan-auth` namespace），使用 `createSecureStorage()` 加密 | `token` | 与 settingsStore 分开防止配置重置清掉登录态 |
| NPC 状态 | `client/src/stores/npcStore.ts` | 管理客户端已认识 NPC 的注册表、关系、交互历史和升格 | `npcs`、关系历史、秘密信息 | 供社交面板、Prompt 注入与组队系统复用 |
| 角色列表状态 | `client/src/stores/characterListStore.ts` | 维护本地角色存档索引，用于标题页继续游玩和读档弹窗 | `savedCharacters` | 属于"角色目录"，不是当前角色详情 |
| 自动游玩状态 | `client/src/stores/autoPlayStore.ts` | 管理 AutoPlay 的执行状态、轮次、最近动作与错误信息 | `status`、`currentRound`、`lastAction` | 供 `AutoPlayControl` 显示执行进度 |
| 多人联机状态 | `client/src/stores/multiplayerStore.ts` | 管理房间信息、玩家会话、角色槽、大厅阶段、行动轮结果与本地联机存档索引 | `roomId`、`players`、`characterSlots`、`localArchives` | 多人 UI 的核心状态中心 |
| 队伍状态 | `client/src/stores/partyStore.ts` | 管理队伍成员、忠诚度、经验、战斗加成与辅助能力查询 | `members`、`maxSize`、`getCombatBonus` | 为判定系统、旅行系统、队伍面板提供共享事实 |
| 战斗状态 | `client/src/stores/combatStore.ts` | 管理 v0.4 战斗系统的 5 阶段状态机 (idle / setup / rolling / acting / resolution / ended) + ACT 队列 + QTE 时序 | `session`、`currentRound`、`pendingActions` | 仅在战斗中持有值，结束后清空 |
| 物品注册表 | `client/src/stores/itemRegistryStore.ts` | 维护 v0.4 affix 词条池的运行时注册表 (前/后缀 + 权重)，供 `applyConsequences` 战利品路径查询 | `affixPools`、`drawAffixes` | 配合 `data/affixPools.ts` 数据层使用 |
| 图鉴状态 | `client/src/stores/codexStore.ts` | 管理 v0.4 Codex 图鉴条目 (npc/item/event/location/faction/lore 6 分类) + 签名去重 + 解锁时间 | `entries`、`unlockedAt` | 配合 `codexSignature` 纯函数防重复 |

### 2.4 核心推理与规则系统（Services / engine、judgment、hooks）

| 系统 | 入口文件 | 主要功能 | 关键协作对象 | 说明 |
|------|----------|----------|---------------|------|
| PM 引擎 | `client/src/services/engine/PMEngine.ts` | 组装 Prompt、协调 Query Protocol、调用 LLM 并解析为场景/叙事响应 | `PromptBuilder`、`LLMClient`、`QueryResolver` | 只返回结果，不直接写 store |
| Prompt 组装器 | `client/src/services/engine/PromptBuilder.ts` | 按世界层、角色层、场景层、上下文层生成 Prompt 文本 | `TokenBudget`、`ContextMerger`、`HistoryCompressor` | Prompt 工程的核心拼装层 |
| Token 预算系统 | `client/src/services/engine/TokenBudget.ts` | 为 Prompt 组件分配 token 预算，必要时生成 Query Hint | `PromptBuilder` | 解决上下文过长时的裁剪策略 |
| 上下文合并 | `client/src/services/engine/ContextMerger.ts` | 去重并排序多源上下文，控制注入优先级 | 世界/NPC/历史上下文 | 面向 Prompt 侧优化 |
| 历史压缩 | `client/src/services/engine/HistoryCompressor.ts` | 将长对话压缩为较短叙事摘要 | 最近消息、LLM 可选压缩 | 结合 token 预算使用 |
| 查询解析 | `client/src/services/engine/QueryResolver.ts` | 处理 PM Query Protocol 中的 inventory/npc/location 等查询 | 各 store | PMEngine 的辅助模块 |
| 本地判定系统 | `client/src/services/judgment/JudgmentSystem.ts` | 执行 2d6 判定，叠加属性、技能、装备、条件、夜间惩罚和队伍加成 | `characterStore`、`partyStore`、系统钩子 | 单人和多人本地判定的统一入口 |
| 条件注册表 | `client/src/services/judgment/ConditionsRegistry.ts` | 维护预设条件效果并提供条件效果解析 | `JudgmentSystem`、旅行/恢复系统 | 让 conditions 不只停留在展示层 |
| 游戏钩子系统 | `client/src/services/hooks/SystemHooks.ts` | 提供命名空间化钩子注册、替换、启停与链式执行 | `services/hooks/rules/*` | 用于解耦跨系统联动 |
| 快照构建 | `client/src/services/hooks/GameSnapshot.ts` | 为钩子执行构建统一的游戏快照 | `gameStore`、`characterStore` | 供规则读取环境/角色上下文 |
| 触发器提取 | `client/src/services/hooks/extractTriggers.ts` | 从 PM 后果或行动中提取可被规则消费的触发事件 | `usePMEngine` | 将 GM 输出映射到钩子命名空间 |
| 规则注册入口 | `client/src/services/hooks/rules/index.ts` | 在应用启动时注册时间、休息、战斗、环境、条件等规则 | `systemHooks` | `App.tsx` 通过 side-effect import 装载 |

| 自动游玩引擎 | `client/src/services/autoPlay/AutoPlayEngine.ts` | 为 AI 玩家生成动作决策循环 | `useAutoPlay`、`usePMEngine` | 面向无人值守或观察模式 |
| 角色卡导出 | `client/src/services/character/CharacterCardExporter.ts` | 从 store 导出角色快照到统一角色卡格式 | `characterStore`、`npcStore` | 面向跨世界/跨故事书迁移 |
| 角色卡导入 | `client/src/services/character/CharacterCardImporter.ts` | 校验并导入角色卡，处理故事书兼容性 | 各 store | 包含版本与基础合法性检查 |
| 事件总线 | `client/src/services/event/EventBus.ts` | 发布/订阅跨模块事件 | `services/event/events.ts` | 用于网络在线状态、世界同步通知等 |
| 缓存管理器 | `client/src/services/cache/CacheManager.ts` | 提供通用缓存能力 | 暂未集成 | 预留系统，后续需决定接入或清理 |

### 2.8 系统边界判断

1. 当前客户端已形成"store 保存事实、hook 负责编排、service 承载规则与 IO"的基本分层，方向合理。
2. `usePMEngine.ts` 目前承担了过多 orchestration 责任，是最值得继续拆分的核心系统。
3. `APIClient.ts` 与 `MultiplayerAPI.ts` 各自维护请求、鉴权和错误处理，网络层未完全收敛。
4. `SyncManager.ts` 与 `SyncServices.ts` 职责边界清楚（世界同步 vs 房间/实时玩家），应保留。
5. `CacheManager.ts`、认证 token 归属、联机 API 与通用 API 的统一方式，是当前最明显的架构补强点。

## 三、运行流程

### 3.1 启动流程

```text
npm run dev / npm run build
  -> main.tsx 挂载 <App />
  -> App.tsx import './services/hooks/rules'
  -> 应用初始化 store、全局模态和覆盖层
  -> 拉取 Storybook 运行时数据 hydrateStorybook()
  -> 根据 phase 和多人房间状态进入标题页、单人游玩或多人视图
```

**标题页阶段**提供四条入口：

1. 创建新角色：打开 `CharacterCreationWizard`。
2. 快速开始：生成 demo 角色并直接进入单人流程。
3. 继续游玩：从 `characterListStore` 载入本地角色。
4. 多人联机：打开 `MultiplayerSetupModal`，进入创建或加入房间流程。

**Storybook 运行时装配**：`App.tsx` 在启动后执行 `hydrateStorybook()`，成功后把标准化故事书数据写入 `worldStore.storybook`。从此刻起，世界名称、时代、起始区域、关键 NPC 和世界 lore 均由故事书运行时提供。

### 3.2 进入单人游戏

`startGame` 负责把角色从"标题页对象"转为"运行时状态"：

1. 将角色写入 `characterStore`。
2. 依据 `resolveRuntimeStartState()` 解析起始区域、子区域、地点、坐标、地形和时间。
3. 回填 `gameStore` 与 `worldStore` 的初始运行状态。
4. 注入日期分割线与初始消息环境。
5. 通过 `storybook runtime` 与 `npcGenerator` 创建起始 NPC。
6. 调用 `initPM()` 初始化共享 `PMEngine`。
7. 请求首个场景 `requestScene()`，正式进入主循环。

当 `phase === 'playing'` 时，`App.tsx` 启动两条长期副作用：

- `ActivityReporter`：周期上报当前玩家活动状态。
- `SyncManager`：启动自动同步与世界更新推送。

返回标题页时这两条副作用停止；如开启 `syncOnExit`，先执行一次强制上传。

### 3.3 单人主循环

```text
InteractionArea / 快捷动作 / 语音输入
  -> usePMEngine.submitAction(action)
  -> 估算 absurdity 并决定是否本地判定
  -> JudgmentSystem 生成骰子结果（或自动成功）
  -> PMEngine 生成组合式叙事结果
  -> applyConsequences 落地到 characterStore / gameStore / npcStore / partyStore
  -> 追加消息流、编年史与本地自动存档
  -> 视需要触发世界同步通知、活动上报、NPC 注册与提示
```

`usePMEngine` 当前同时承担：单人动作提交与本地判定、多人轮次结果消息同步、后果应用（属性、状态、物品、条件、关系等）、编年史记录与本地角色自动保存、钩子系统触发（驱动时间流逝、休息、环境和条件联动）。

**PM 请求链**：`PMEngine` 拼装以下上下文为一次性 Prompt——世界层（时代、lore、故事书指导）、角色层（属性、技能、装备、状态、队伍信息）、场景层（结构化位置、地形、天气、已知/幽灵 NPC）、上下文层（最近消息、叙事摘要、必要时压缩）、查询协议（token 紧张时按需回填 inventory/npc/location）。

### 3.4 多人联机流程

**大厅与开始游戏：**

```text
MultiplayerSetupModal
  -> createRoom / joinRoom
  -> multiplayerStore.syncRoomSnapshot()
  -> LobbyPanel 渲染玩家、角色槽和房主控制
  -> character-ready / common backstory / start
  -> room.state.phase 进入 playing
  -> App.tsx 切换到 MultiplayerGameView
```

**行动轮同步**由 `SyncServices.ts` 管理：

- `startHeartbeat()`：30 秒保活。
- `startRoomPoll()`：5 秒轮询房间快照。
- `startRoundPoll()`：3 秒轮询行动轮状态；全员已提交且无最新结果时主动调用 `processRound()`。
- `usePMEngine`：消费轮次结果，写回消息系统并对当前玩家应用后果。

**中途加入与观战：**

1. 游戏进行中允许中途加入时，新玩家进入 `spectating`。
2. 完成 `spectator-ready` 后进入 `pending_intro`。
3. 行动轮推进到满足 `late_join_intro_delay` 后，服务端在多人 PM 叙事中正式引入该玩家。
4. 引入成功后状态切换到 `in_game`，后续可正常提交行动。

### 3.5 世界同步与活动上报

**世界同步**：`SyncManager` 在单人 `playing` 阶段启动后维护两条通道：

1. 轮询同步：定时执行 `syncAll()`，上传编年史并拉取 `/api/v1/sync/updates`。
2. SSE 推送：连接 `/api/v1/world/stream`，服务端推送世界更新时直接回写 `worldStore`。

同步结果统一落到：`worldStore.currentWorldDay`、`regions`、`worldChronicle`、`ghostNPCs`、`pendingEncounters`。

**活动上报**：`ActivityReporter` 周期上报玩家当前位置、行动与在线状态，属"观测性数据通道"，不直接改变客户端主流程。

### 3.6 扩展能力流程

- **AutoPlay**：`useAutoPlay` 通过 `AutoPlayEngine` 生成动作，复用 `submitAction` 主管线，与手动游玩共享同一套判定、后果和存档逻辑。
- **语音输入/输出/插画**：`useVoiceInput` 优先使用 Web Speech API，必要时回退 STT；`TTSClient` + `NPCVoiceManager` 负责朗读和音色持久化；`ImageClient` 负责地形插画与 NPC 立绘生成，使用 IndexedDB 缓存。这些能力属于"围绕主循环增强体验"的旁路，不反向侵入主状态管理边界。

## 五、规划

当前构建已稳定通过 66 项测试，主包体积控制在 383 kB，为后续特性拓展提供了扎实的工程基础。

在 AI 驱动的游戏体验上，期望 AutoPlay 从当前的单一路径发展为多策略决策体系——冒险型、谨慎型、社交型等风格并存，让 AI 角色在交互中呈现更丰富的个性层次。实时同步方面，计划以 WebSocket 替代 HTTP 轮询，实现更低延迟的多人协同体验。同时将推进移动端响应式适配，使界面自然拥抱触摸交互。

在全球化与离线能力方面，将建设国际化框架，实现英文 UI 与多语言 Prompt 模板体系。持久化存储也将从 localStorage 迁移至 IndexedDB，带来更大的存储容量和更结构化的数据管理。在此基础上引入 Service Worker，使客户端具备离线可用的渐进式能力。

长远来看，期望交付 Tauri 桌面端应用，获得原生级的性能与系统集成。同时构建插件系统，打开第三方扩展的入口，并以此为基石孵化社区模组市场，让艾瑟兰的生态从开发团队延伸到每一位玩家。
